# jRelay codebase audit — September 2026

Full-codebase adversarial audit at v5.4. 24 agents dispatched across 7 code areas and 15
cross-cutting lenses; **23 delivered**. Every finding below was verified against the source by the
architect, not taken on an agent's word. Findings the agents raised that did not survive that
check are not listed.

**Coverage note:** the dedicated *member-lifecycle* lens never reported. Most of that ground was
covered from other directions — the database, command-handler, mode-matrix and contracts passes
produced the `reactivate` column omissions, the nickname-uniqueness and resolution defects, and
the zero-admin trap. The three questions in that brief that no other agent was asked were
answered directly by the architect and appear below as 2.11, 2.12 and 3.22.

Ordered by what it costs, not by where it lives. The top tier is not "worst bug" — it is
"threatens the one thing this app exists to do", which is keep a single consumer line inside
CTIA person-to-person guidelines so ~100 neighbours can share a text group.

## Status

**Closed in v5.5** (first remediation wave): 0.1 debuggable APK · 2.9 backups · 1.1 failure-alert
feedback loop · 2.2 zero-admin trap (all four paths) · 3.1 pause cancelled by opening Settings ·
3.2 pacing ceilings (clamped on read as well as save, so existing installs are covered) ·
3.8 empty-body fan-out · 3.13b stranded-branch duplicate send · 3.13c unguarded mutators ·
4.1 `stripLeadingWord` · 4.5 locale-sensitive `toLowerCase`.

**Next wave, in this order:**
1. **3.13a — the remaining duplicate-send window.** Branch 1 of `resetOrphanedSending` still
   matches "result landed, terminal write not yet committed". v5.5's token guards narrowed it but
   **slightly widened one half**: the previously-unguarded `markSent`/`markFailed` would stamp over
   a stray reset and accidentally heal it, and now correctly do not. This is now the widest
   remaining hole. Fix is atomic resolution — `recordPartSent` and `recordSendFailure` moving the
   row out of `SENDING` in the same transaction. Once branch 1 stops leaving rows in a
   SENDING-matchable state, the guards added in 5.5 reject stale results automatically, with no
   call-site changes.
2. **The drain thread's missing `catch`** — and, in the same change, moving
   `resetOrphanedSending()` inside the `DRAINING` try/finally. Doing the first without the second
   turns a loud crash into a permanent silent stall.
3. **2.3 / 2.11 — newline sanitisation and nickname validation** (the `[Admin]:` forgery), plus the
   Unicode-digit fix in `normalize` that closes the duplicate-member path.
4. **1.2 / 1.3 — re-denominate the daily cap in segments and move the check into `enqueue`**, the
   funnel all eleven fan-out paths already share.
5. **0.2 — the release signing config.** Needs a keystore decision from the owner; until then there
   is no working release build and the debug keystore is a single point of failure for in-place
   upgrades.

Everything above is code. None of it removes the need for the device checklist — six releases
(5.0-5.5) remain unverified on hardware, and the database-layer findings can only be confirmed
there.

## 0. Ship-blocker for the current APK

**0.1 The debug APK is debuggable.** `android:debuggable="true"` is in the merged manifest
(`app/build.gradle.kts` declares no `debug {}` block, so AGP's default applies). `adb shell
run-as com.sh7411usa.jrelay` then reads `databases/jrelay.db` — every member's phone number and
the complete message log — with no root. The relay phone is plugged into a PC as a matter of
routine, because that is how `WRITE_SECURE_SETTINGS` gets granted. Do not put this build on a
phone holding real members' data.

**0.2 There is no signing config and no release path.** `release` has no `signingConfig`, there
is no `signingConfigs` block, and no keystore is referenced anywhere. The installed build is
signed by the auto-generated `~/.android/debug.keystore` on one Windows machine, which is not in
version control and not backed up. Lose that machine and every `adb install -r` fails
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` permanently; the only recovery is `adb uninstall`, which
deletes the database — all members, admin flags, and history. `assembleRelease` today emits an
unsigned APK that cannot be installed at all.

## 1. The carrier line — the reason the app exists

The pacing half is correct and was verified independently: **36.6 messages/minute, 2m43s for a
100-member fan-out** (~3m28s including the coalescing hold), inside the 15–60/min band and
consistent with the README. There is exactly one `SmsManager` call site in the app, and every
outbound message reaches it through the paced drain. Rate control works.

Volume control does not.

**1.1 The failure-alert feedback loop.** `alertAdminsOfFailures` (`CommandProcessor.java:549`)
skips only `isMuted` — it has **no `admin.id == target.id` guard**, unlike its sibling
`sendToAdminsOnly` (`:228`) which does. So the alert *about* a failing admin is sent *to* that
admin, and because `enqueue(admin, ...)` stamps the row with the admin's own `member_id`, a failed
alert increments the very counter that fires alerts.

The severity needs stating precisely, because the naive reading overstates it. `failed_count` is
a **ratchet, not an escalator**: the alert test is `failedCount % threshold == 0`, which fires at
a fixed one-per-threshold rate at any magnitude, and `resetFailedCount` *does* clear it — but only
via one narrow path (`SentReceiver.java:201`, requiring a clean single-part delivery that still
matches `status='SENDING' AND handed_off_at=token`). It therefore never clears for a dead or
ported number, and for Hebrew/Yiddish traffic — UCS-2 at 70 chars/segment, so multi-part is the
*normal* case here — a partial success zeroes `parts_pending` and credits no reset either.

So the gain is not admins ÷ threshold generally; it is **(admins whose count never resets) ÷
threshold**. Unaided divergence needs that ratio ≥ 1: at threshold 1 (allowed) a single dead admin
number self-sustains at roughly **1,000 SMS/day forever, surviving reboots**; at the default
threshold of 3 it needs four or more dead admin numbers. But it does not need to diverge to hurt —
with 30 posts/day one dead admin number already fails ~30×/day, so alerts run ~10/day
indefinitely, and they fire on `NO_SERVICE`, `RADIO_OFF` and carrier rejection. The app's response
to "this line is in trouble" is to put more traffic on it.

Still the highest-value fix on this list: one `if (admin.id == target.id) continue;`, with the
precedent already sitting 300 lines above it.

**1.2 The daily cap counts the wrong unit, twice over.** `countRelayedSince`
(`MessageRepository.java:121`) counts `category='RELAYED' AND direction='IN'`, and `postToGroup`
logs exactly one such row per post. The ~99 outbound copies are never counted. So a cap of "100"
permits ~9,900 messages. Carriers meter *segments*, not messages, and nothing in the codebase
counts segments — worst case measured at **990× the labelled cap**. The cap is also **disabled by
default**, so as shipped there is no volume limit of any kind.

**1.3 The cap is checked on 1 of 11 fan-out paths.** `postToGroup` is the only enforcement site.
Uncounted and uncoalesced: `#name`, `#stop`, `#admin`, `#list`, join replies, mode-change
notices, group renames, add/remove notices, admin broadcasts, reply-copies, and CSV import.
Worst case: importing a 100-row CSV into a 100-member group is **10,000 messages from one button
press**, with no confirmation and no count shown.

**1.4 `#name` is a 100× amplifier available to any member.** No admin gate; `enqueue`
(`:820`) applies the coalescing hold and salt only to `CATEGORY_RELAY`, so the rename broadcast
is never merged and never counted. Alternating two nicknames defeats the `.equals` short-circuit.
Ten texts a minute queues 1,000 messages against a 36.6/min drain.

**1.5 "Clear History" refills the day's quota.** Usage is derived live from `message_log` and
`clearHistory()` deletes the table, so a host who hits the cap and then tidies the feed gets a
second full day's allowance. The dialog says it only clears feeds and stats.

**1.6 Multipart bypasses microspacing.** `MicroSpacer` runs between `sendOne` calls, never
between parts; `sendMultipartTextMessage` hands every part to the radio at once. A burst of four
3-segment messages is 12 segments in ~1.05s.

**1.7 The merged-segment cap is a sample, not a bound.** `SmsSendService.java:272` sizes
candidates using one random ZWSP draw and `:431` salts with an independent draw. A body measured
at 3 segments can ship as 4, for every recipient of that merge.

**1.8 `#join` flooding.** `#join` is evaluated before the member lookup, so any stranger can
trigger one SMS to every admin plus a reply to an unverified number, repeatedly, with no dedupe.

## 2. Harm to the people in the group

**2.1 One English word removes a member.** Bare keywords are on by default and matched as whole
strings. A member answering "should we cancel tomorrow?" with **"Cancel"** is soft-removed with
no confirmation, and 99 neighbours are told they left. Recovery is dead: `#join` hits
`JoinPolicy.OFF` and returns silently. Same for END and QUIT.

**2.2 The last admin can orphan the group permanently.** `handleStop` has no admin-count check,
so the last admin texting `STOP` empties `getActiveAdmins()` and every admin gate then fails
closed forever. Verified unrecoverable over SMS: `setAdmin` has exactly one call site
(`MemberDetailActivity.java:93`), and `reactivate` sets `is_admin = 0`, so re-adding them returns
them as a non-admin. Recovery requires physically holding the handset.

**2.3 Any member can forge an admin broadcast, with no trace.** `MessageMerger` joins coalesced
posts with `"\n"`, so a merged message legitimately reads `Alice: x⏎Bob: y`. Nothing strips
newlines from inbound bodies. A member texts a body containing a newline followed by
`[Admin]: ...` and it arrives structurally identical to a genuine coalesced line — `[Admin]: ` is
byte-for-byte the app's own prefix. No rename notice, no marker, nothing. The nickname route
(`#name [Admin]`, `#name @system`) achieves the same with one easily-missed notice.

**2.4 `#to` can be hijacked by nickname-prefix extension.** The resolver keeps the *longest*
resolving word-prefix, so an attacker naming themselves `Bob can` intercepts
`#to Bob can you pick up the kids at 4`. The sender gets no confirmation and never learns.

**2.5 A nickname that looks like a phone number shadows the real one.** `resolveMemberTolerant`
tries nickname before phone, so a member naming themselves `+15551234567` causes the admin's
`#remove +15551234567` to remove the *attacker* and leave the intended target in place.

**2.6 STOP does not stop.** `softRemove` sets `active=0` and nothing else; the drain selects on
status and hold time only and never re-checks membership. A member who texts STOP keeps receiving
every already-queued message — dozens over the following half hour. Continuing to text after an
explicit STOP is the one compliance rule with no grey area.

**2.7 A private message to a muted member evaporates silently.** `deliverReply` skips the enqueue
and returns without telling the sender, who explicitly addressed one person.

**2.8 A mode change is instant but its notice is paced.** A member who has not yet received the
notice can send a message they believe is private and have it broadcast to everyone.

**2.9 Backups are on.** `allowBackup="true"` with both backup XML files left as unmodified
Android Studio templates, so `jrelay.db` goes to the operator's Google account and into
device-to-device transfer. None of the ~100 people consented to their number leaving the phone.

**2.11 One person can get two member rows, and then receives everything twice.** `phone_e164` is
`UNIQUE`, so two *identical* normalised strings cannot both exist — but `normalize` tests with
`Character.isDigit(c)` and appends **the original character**, not its ASCII value.
`Character.isDigit` is true for every Unicode decimal digit, so Arabic-Indic input normalises to
`+1٢٣٤٥٦٧٨٩١٠`, a different string from `+12345678910`. The UNIQUE constraint does not fire and a
second row is created for the same human, who then receives every group message twice — doubling
their share of a capped daily budget, and doubling their visibility of it. Reachable from Add
Member, Member Detail's edit-number dialog, and CSV import; `#add` is protected only because its
regex splitter uses ASCII-only `\d` and rejects the input first. The same defect also means that
member's inbound texts arrive as ASCII and fail the lookup, so they are not recognised as a member
at all. One-character fix: `c >= '0' && c <= '9'`, or fold via `Character.digit(c, 10)`.

**2.12 The dashboard's member count and the relay's actual reach disagree.** `getActiveMembers()`
selects `active = 1` with **no mute filter**; `getActiveRecipientsExcept()` selects
`active = 1 AND is_muted = 0 AND id != ?`. The first backs the dashboard count, `#list`, the
Membership screen, "Apply to All Members" and `broadcastToGroup` (Send to Group); the second backs
the actual relay fan-out. So with ten muted members the dashboard reads "100 members" while a post
reaches 89. A host sizing the daily limit against the number on screen is working from the wrong
figure, which compounds 1.2. (Send to Group reaching muted members is deliberate and documented;
the dashboard and `#list` disagreement is not.)

**2.10 CSV formula injection.** `escapeField` handles only `,`, `"` and newline. A nickname
beginning `=` becomes a live formula when the roster is opened in Excel, and the adjacent cell is
a phone number.

## 3. The relay stopping without telling anyone

**3.1 Opening Settings cancels an active pause.** The spinner listener is attached before first
layout, so `AdapterView` fires `onItemSelected(0)` with no user input. The guard
`if (getPauseUntilMillis() != 0)` means it does nothing when unpaused and fires **only when
paused** — clearing the pause and dumping the backlog before the host touches anything.

**3.2 Pacing has floors but no ceilings.** Every clamp is `Math.max`; the only `Math.min` is on
the coalesce window. `minWait=0` with `maxWait=2147483647` overflows `random.nextInt` to a
negative bound → `IllegalArgumentException` on the drain thread, which catches only
`InterruptedException` → the drain dies. A large-but-valid wait puts the thread into a multi-year
sleep, and because `RateLimitConfig` is snapshotted once per drain, changing the value back has
no effect — force-stop is the only recovery.

**3.3 A denied permission is never detected.** `ConsentActivity.java:65` ignores `grantResults`
entirely and calls `goToMain()` unconditionally. Deny SMS or notifications at first run and the
app looks configured while every send throws `SecurityException` (swallowed) or every alert is
silently discarded. Consent never re-runs, so there is no in-app way to recover.

**3.4 The alert channel has three independent failure modes.** There is no `cancel()` call
anywhere, so alerts accumulate to Android's ~50-per-package limit after which `notify()` silently
discards; `notificationCounter` is a non-volatile static read-modify-written from two threads, so
ids collide and one alert replaces another; and 3.3 above can disable the channel entirely.

**3.5 A forward clock jump can duplicate up to 100 messages.** `resetOrphanedSending` derives
both its staleness cutoff and its boot-time cutoff from the wall clock, while `handed_off_at` is
also wall-clock. An NTP correction during a fan-out makes every in-flight row look stranded; they
are re-sent while the originals are still delivering. A backward jump strands rows that nothing
recovers, and inflates `countAwaitingResults` so every drain exit burns its full 60s.

**3.6 A stuck pause silently drops inbound posts.** `handleIncoming` returns immediately while
paused — messages are discarded, not queued, and not logged. A reboot before network time (or a
dead RTC) can leave the app paused far past the intended window, swallowing every post with no
trace.

**3.7 `Thread.sleep` between bursts does not advance during device suspend.** The other two wait
loops re-read the clock every 5s and recover; this one does not. Screen off, a fan-out can resume
long after the dashboard says the next burst is due.

**3.8 A blank SMS broadcasts an empty post to all 99.** No guard for an empty trimmed body; it
falls through to `relayPlainMessage` and burns a quota slot.

**3.9 The fan-out is not atomic.** ~200 individually-committed inserts on the main thread inside
`onReceive`. A kill partway leaves some members queued and the rest never, with the post already
marked relayed and the quota already charged.

**3.10 A failed log insert poisons reply targeting for everyone.** `log()` returns `-1` on
failure; `postToGroup` stores it in a primitive `long` and passes it to a `Long` parameter whose
guard is `!= null`, so `-1L` passes and every recipient's `last_post_received_id` becomes `-1`.

**3.11 `onDowngrade` is not overridden.** The default throws, so rolling back to an older APK
puts every database open into a permanent failure — recoverable only by wiping all members.

**3.13 Two duplicate-send paths that need no clock jump.** Both are in the send pipeline that
five prior reviewer rounds passed.

*(a)* `resetOrphanedSending` branch 1 matches `status='SENDING' AND parts_pending=0`, and its
javadoc asserts that state can only mean "claimed by `takeBurst`, killed before `markHandedOff`".
It also means **"the result landed and the terminal write has not committed yet"** —
`recordSendFailure` explicitly writes `parts_pending=0` while leaving status `SENDING` for the
whole of `handleFailure`. `SentReceiver` runs on the main thread; a drain worker running
`resetOrphanedSending` concurrently flips the row to PENDING without bumping `attempts`, and
`takeBurst` reclaims it milliseconds later. The recipient gets it twice. The javadoc's two safety
preconditions reason only about competing *drains*; neither excludes a concurrent `SentReceiver`.

*(b)* The **stranded** branch of the same method sets `status='PENDING', attempts = attempts + 1`
but leaves `parts_pending > 0` and `handed_off_at = <old token>` intact on a row it has just
declared dead. `takeBurst` then re-claims that row writing **only** `status`, so between the claim
and `sendOne`'s `markHandedOff` the row once again fully satisfies `recordSendFailure`'s match
clause — `id = ? AND status='SENDING' AND parts_pending > 0 AND handed_off_at = ?` — for the
*abandoned* attempt. A late result from that dead attempt therefore returns true, `handleFailure`
calls `requeueForRetry`, and a mid-send row is flipped to PENDING and drawn again. With
microspacing, that window is seconds wide for later rows in a burst. **Fix: add
`parts_pending = 0` to that UPDATE — one token.** (The sibling `neverHandedOff` branch is safe
because it already matches on `parts_pending = 0`.)

*(c)* `requeueForRetry`, `markSent` and `markFailed` are unguarded `WHERE id = ?` writes, while
**every other mutator in that class is guarded** (`recordPartSent`, `recordSendFailure`,
`applyMerge`, `takeBurst`). So the main thread's `handleFailure` can stamp PENDING over a live
`SENDING` claim; that send's real result is then discarded as stale, and the row is drawn again —
a third copy, repeating until `attempts` exhausts. Fix is the contract `recordPartSent` already
implements: add `AND status='SENDING' AND handed_off_at = ?`.

**3.14 The hand-off window cannot distinguish "never sent" from "sent, no result yet".**
`markHandedOff` commits *before* the radio call — which is the correct order, since recording
afterwards would let a fast result find `parts_pending=0` and be discarded. But it means a death
before the radio call and a death after the radio accepted the message leave **identical database
state**, and `resetOrphanedSending` must guess. It guesses "resend". The stranded branch also
bumps `attempts` without consulting the retry limit, so it can resend a row that already exhausted
its retries. A `dispatched` flag set immediately after `SmsManager` returns would separate the two
cases.

**3.15 Inbound has no idempotency key, and the platform may re-dispatch.** `handleIncoming`
stores nothing identifying a message — no PDU hash, no sender+timestamp key. AOSP keeps an
undelivered inbound SMS and re-dispatches it when a broadcast never completed, which is exactly
what the non-atomic fan-out (3.9) makes likely. A second run re-enqueues to all 99, so everyone
already served gets the post twice. (Platform re-dispatch is environment behaviour, not verifiable
from this repo; the verifiable half is that the pipeline has zero tolerance for it.)

**3.16 A malformed PDU crashes the inbound path.** `SmsMessage.createFromPdu` returns **null** for
an unparsable PDU, but the array stays non-null and non-empty, so the existing length guard misses
it. One bad PDU is an NPE in `onReceive` — process crash, and the SMS is gone, since broadcasts
are not redelivered.

**3.17 Opening the app does not restart a stalled queue.** Of the 14 `SmsSendService.start()`
call sites, **none is in `MainActivity`**. So after any stall the host opens the app, sees
"Messages in Queue: 47", and opening it kicks nothing. One line in `onResume` fixes it.

**3.18 A post arriving while paused is destroyed.** The pause check returns *before* the inbound
log, so nothing is queued, logged, or replied to — unpausing recovers nothing and the senders
believe the group received them. Note the two pause checks disagree with each other:
`drainAll`'s correctly leaves rows PENDING and resumes.

**3.19 A merged row collapses N posts into one failure.** Merge folds several posts into one
outbox row, but all failure accounting is per-row: four merged posts to a dead number cost four
lost posts, one FAILED log row, and **one** failure-count increment. Delivery-failure visibility
drifts low by exactly the merge factor — the wrong direction for the one signal that says a
member's number has gone bad.

**3.12 No indexes, no pruning.** Not one `CREATE INDEX` in the schema. ~101 log rows per relayed
post (~737k/year), the outbox is never pruned of completed rows, and the dashboard runs
unindexed full scans — including `ORDER BY timestamp DESC LIMIT 20`, which sorts the entire
table — on the main thread at 1 Hz. `SmsReceiver` calls `handleIncoming` directly on the main
thread with no `goAsync()`, inside a broadcast with a ~10s budget and **no redelivery**: exceed
it and that inbound message is gone permanently.

## 4. Correctness and presentation

**4.1 `stripLeadingWord` splits on a literal space.** `#admin` followed by a newline yields an
empty argument and the handler returns with **no reply at all** — silently dropped. Affects seven
commands. The identical bug was found and fixed in `#to` and `stripPostPrefix`.

**4.2 Commands fail silently on an unresolved target.** `#remove Sara` when the nickname is
`Sarah` returns bare, with no reply. The admin believes the removal worked. `tpl_to_not_found`
already exists and is used elsewhere — this breaks the file's own convention.

**4.2a `#to` with a phone number never delivers.** `PhoneNumberUtils.normalize` harvests digits
from anywhere in the string and ignores everything else, so `normalize("5551234567 hi there")`
equals `normalize("5551234567")`. `handleToCommand` keeps the *longest* word-prefix that resolves
to a member, so every longer candidate keeps matching until the prefix consumes the whole input
and the message is empty — the sender gets the usage error and the target gets nothing. Two
reproducible forms: `#to 5551234567 hi there`, and any nickname-addressed message that happens to
end in a phone number (`#to Bob call me at 555-123-4567`). The same looseness is what makes the
`#to` prefix hijack (2.4) and the nickname/number shadowing (2.5) possible, so one strict-parse
fix closes three findings.

**4.3 Any message starting with `#` is swallowed.** `#2 on the list is the fence` becomes
"Unknown command" and the group never sees it. Hashtag-leading messages are ordinary in a group
chat.

**4.4 Dashboard counters are wrong.** "Messages Today"/"Total" count one row per *recipient*, so
they read ~100× high; per-member "sent" double-counts every relayed post; the member activity
band counts messages *received*, so a silent member is labelled "High activity"; and the two
"Today" figures on screen use different windows (rolling 24h vs the quota's calendar window).

**4.5 Three `toLowerCase()` calls have no explicit `Locale`.** Latent — Hebrew and Yiddish are
unaffected, Turkish/Azeri would break every command. The codebase already uses `Locale.ROOT` and
`Locale.US` elsewhere, so these are oversights.

**4.6 Command tokens render reversed for Hebrew and Yiddish readers.** `#` is bidi class ET, so
at the start of an RTL line the token lays out as `commands#`. Copy-paste works; retyping does
not. No LRM/RLM/isolate characters exist anywhere in the three string files. This is invisible to
an English-reading reviewer and affects the languages the members actually read.

**4.6a Every outgoing SMS ignores the Language setting.** `LocaleThemeUtil.wrap` is called from
exactly one place — `BaseActivity` — and returns a *new* Context rather than mutating the
application Context. There is no `Application` subclass. `CommandProcessor` pins
`getApplicationContext()` in its constructor, so all 69 `getString` sites in `sms/` and `util/` —
every relay prefix, welcome message, command reply, mode notice, join request and failure alert —
resolve against the **device** locale. `Locale.setDefault` does not help, because resource
selection reads `Configuration.getLocales()` off the Resources object.

Consequence: a host whose phone is in English who selects Hebrew or Yiddish gets a translated UI
and **English text messages to every member**. The dominant path on a relay phone is a cold
process start from `SmsReceiver`'s broadcast, where no Activity has ever run — so `values-iw` and
`values-yi` are, for outbound SMS, effectively unreachable. All 326 strings are translated and
verified correct; almost none of them are ever sent. Fix: an `Application` subclass overriding
`attachBaseContext`, or hold a wrapped context in the four non-Activity classes.

**4.6b An invisible RTL mark defeats every prefix check.** `body.trim()` strips only characters
≤ U+0020, so U+200F / U+200E — which Hebrew and Yiddish keyboards routinely prepend — survive.
`‏#stop` is therefore **relayed to all 99 members** instead of removing the sender, and `‏#all x`
misses the `^`-anchored post pattern, so in Reply Mode a message meant for everyone goes to one
person. The app ships both those keyboards' languages.

**4.7 `targetSdk 36` with no inset handling.** Edge-to-edge is enforced on Android 15+; zero
occurrences of `fitsSystemWindows`, `WindowInsets`, or the opt-out anywhere. Header text renders
under the status bar and the last control of every screen sits under the gesture pill — on the
small screens this app targets, that is a large fraction of usable height.

**4.8 `#stop`, `Call`, `Text` and `Export Contact` can crash.** Three unguarded implicit
`startActivity` calls; a stripped relay phone with the dialer or Messages disabled throws
`ActivityNotFoundException`.

**4.9 `stripPhoneNumbers` deletes ordinary numbers from relayed text.**
`"prices are 100 200 3000 today"` → `"prices are today"`. Default off.

**4.10 Two one-click paths text all ~100 members with no confirmation** — the Send Group Message
button and the Options-menu mode switches. Removing a single member *is* confirmed.

## 5. Verified clean — do not re-audit

These were specifically hunted and found sound. Recording them so the next pass spends its effort
elsewhere.

- **String format arguments: all consistent.** 59 argument-bearing strings, 92 specifiers,
  compared across all three locales by index, count and conversion type — zero mismatches. All
  positional, none bare. 77 call sites checked; every `%d` receives an `int`. This was the single
  most likely source of a Hebrew-only runtime crash and it is clean.
- **No command token is translated** in Hebrew or Yiddish. Zero differences across all 326 keys.
- **Phone-number normalisation is consistent** across all six call sites — inbound, add-member,
  CSV, and command resolution all use the same function. The classic duplicate-member bug is
  absent.
- **Exported components are sound.** `SmsReceiver` is guarded by both `BROADCAST_SMS` and a
  protected broadcast; `BootReceiver` likewise; `SentReceiver` and `SmsSendService` are not
  exported; `MainActivity` reads no intent extras.
- **All three `PendingIntent` sites pass `FLAG_IMMUTABLE` explicitly.**
- **No SQL injection is reachable.** Nicknames and topics reach the database only via
  `ContentValues`; the three concatenating call sites use compile-time constants or generated
  placeholders.
- **No hardcoded secrets, no external-storage writes, no network code, no `INTERNET` permission.**
- **The migration ladder is correct** for every start version 1→6; `onCreate` and the migrated
  schema match exactly. The only migration defect is the missing `onDowngrade`.
- **Every admin command's gate runs first**, each handler has exactly one call site, and no
  dispatch branch is unreachable.
- **A command reply can never be broadcast**, and a Reply-Mode reply cannot reach a third party —
  verified against the recipient query, not the comments.
- **No reachable unhandled throw in the command handlers**, confirmed independently twice.

## 6. Test coverage

71 tests, and the distribution does not match the risk: 28 on message parsing, 20 on
`SentReceiver` (13 of those on a static string table), 12 on the merger, 6 on phone numbers, 4 on
CSV, 1 asserting 2+2=4. The outbox state machine, the retry path, the quota arithmetic and every
relay content transform have **zero**.

Identified as passing for the wrong reason: the merger suite injects a deterministic counter, so
it proves "the merger honours its counter" while the names imply "a merged body never exceeds the
cap" — which 1.7 shows is false. A distinctness test passes even if every mapping is wrong. One
test asserts a constant equals its own literal. A `now` parameter is passed to a code path that
returns before reading it.

Five of the confirmed bugs are not unit-pinnable without a device, because they live in the
database layer. The ones that *are* cheaply pinnable today, in plain JUnit with no new
dependencies: newline sanitisation of relayed bodies, a bounded ZWSP injection count, the pacing
arithmetic never throwing, nickname validation, and `stripLeadingWord` handling any whitespace.

**3.22 Self-removal leaves its messages sitting in the queue.** `handleStop` and `removeMember`
produce the same database state, but not the same behaviour: the admin path ends with
`SmsSendService.start(context)` and the self-removal path **does not**. So when a member texts
`STOP`, their own confirmation and the "X left the group" notice to everyone else are enqueued and
then wait for some unrelated event to trigger a drain — on a quiet night, potentially hours. This
compounds 3.17 (opening the app doesn't kick the queue either), and it is worst on exactly the
message that should be prompt: the acknowledgement that someone's opt-out was honoured. They also
use different categories (COMMAND vs SYSTEM), though both get `holdUntil = 0` so neither is
coalesced.

**3.20 Draining a backlog is quadratic.** `takeBurst` selects **every** matching pending row with
a null projection (all columns, including bodies) and no `LIMIT` even when shuffle is off, maps
them all, then discards all but the burst size. `takeReleasedRelayRows` is likewise unbounded and
runs at the top of *every* loop iteration, so already-merged rows re-enter `MessageMerger` on each
pass — each candidate costing a real `SmsManager.divideMessage` call. A 1,000-row backlog after an
outage drains at roughly 250 bursts × 1,000 row materialisations, with ~1,000 `divideMessage`
calls per burst. Not a correctness bug; pure cost, in exactly the situation where the queue is
already behind.

**3.21 Raising the wait during a backlog does nothing.** `RateLimitConfig` and the shuffle flag
are snapshotted once at drain start, and `drainAll` does not return until the outbox is empty. An
operator watching a 1,000-row backlog push too fast raises min/max wait in Settings — and the
running drain keeps the old cadence for the entire multi-hour drain. `isPaused()` and the coalesce
window *are* re-read every iteration, so this is specific to these two. The control silently does
nothing in precisely the situation that makes someone reach for it.

## 7. Traps for whoever fixes these

**Do not add a `catch` to the drain thread without also moving line 123.** The drain worker has
no `catch` at all (only `finally`), so any `SQLiteException`, `notify()` failure, or throw inside
`handleFailure` kills the process mid-fan-out. The obvious fix is a catch-all. But
`resetOrphanedSending()` at `SmsSendService.java:123` runs **after** the CAS wins `DRAINING` and
**before** the try/finally that releases it. A throw there today leaves `DRAINING` true with no
owner — and every subsequent `start()` suppresses into `RERUN`, which only the dead thread could
consume. The outbox never drains again. That is currently masked *because* the uncaught throw
kills the process and the static dies with it. **Adding the catch-all without moving line 123
inside the try/finally converts a loud crash into a permanent silent stall.**

**`markHandedOff` before the radio call is correct — don't "fix" the ordering.** Recording after
the send would let a fast delivery result find `parts_pending=0`, be discarded, and strand the
row for a later reset-and-resend. The defect is the missing `dispatched` flag (3.14), not the
order.

**`AUTOINCREMENT` on `message_log.id` is load-bearing.** "Clear History" leaves every member's
`last_post_received_id` pointing at deleted rows; `AUTOINCREMENT` guarantees those ids are never
reused, so reply targeting degrades safely to "no target". With plain rowid reuse a stale pointer
would eventually match an unrelated new message and deliver a private reply to the wrong member.

**One strict phone-parse fix closes three findings** (2.4, 2.5, 4.2a). `normalize` harvesting
digits from anywhere is the shared root.

**The only real prefix collision in the dispatch chain is `#topic`/`#to`, and it is already
guarded.** `"#topic".startsWith("#to")` is true, which is why that branch carries an explicit
whitespace check and an explanatory comment. An earlier draft of this document claimed `#admin`
and `#add` were a second fragile pair; that is **wrong** — `"#admin"` and `"#add"` diverge at
index 3 (`m` vs `d`), so neither is a prefix of the other and their dispatch order is immaterial.
Recorded here because the false claim was believed long enough to reach a fix brief: verify a
prefix relation before treating it as load-bearing.

## 8. Suggested order

1. **0.1, 0.2** — before this APK touches a phone with real numbers.
2. **1.1** — the feedback loop. Cheapest fix on this list with the worst consequence.
3. **2.1, 2.2** — a single English word removing a neighbour, and the unrecoverable
   zero-admin state.
4. **2.3** — newline sanitisation plus a nickname character filter. One pure function closes
   both forgery routes.
5. **3.1, 3.2** — the pause bug and the pacing ceilings; both are a handful of lines.
6. **1.2, 1.3** — re-denominate the cap in segments and move the check into `enqueue`, the funnel
